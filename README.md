# mbui — a MoonBit UI framework

mbui is a cross-platform UI framework written in MoonBit: one core that
builds, lays out and paints a tree every frame and draws everything itself on
the GPU, and thin hosts that put it on the screen and feed it input — macOS
and iOS (Metal), Windows (Direct3D 11), Android (OpenGL ES), and a WebGL2
host for tests and previews. Its flexbox passes Yoga's tests and its text
segmentation Unicode's own. It is what [still.fail](https://still.fail)'s
native clients are being rebuilt in: that app, its design system and pages,
live in still.fail's repository (`apps/mbui`, built by these scripts with
`MBUI_APP_MOD`); so does the player (`src/player`) for now, as it draws with still.fail's design system (it can come
back as framework once it takes its icons and theme from its caller). It is experimental: APIs change without notice.

Open source under the MIT licence (`LICENSE`); what it includes or is
derived from others' work is listed, with their licences, in
`THIRD_PARTY_NOTICES.md`.

```
src/ui      the framework (MoonBit, target independent)
  node.mbt    the tree: pooled nodes linked by index
  layout.mbt  flexbox subset (row/column, gap, padding, align, justify, fill)
  text.mbt    shaping cache, line breaking (UAX #14), caret geometry, lines
              reordered right to left (UAX #9), words of joining scripts
              and ligatures drawn whole
  rich.mbt    rich text: runs (bold, italic, code, links, strike…) in one
              paragraph, wrapped as one text; offsets, carets and rects
  nav.mbt     a stack of pages: pushed and popped sliding, swiped back from
              the left edge or by the system's back gesture
  motion.mbt  CSS curves (cubic-bezier) for timed motion
  list.mbt    virtual list, rows of any height, anchored scrolling, fling
  editor.mbt  multi-line text field with input-method composition
  code_field.mbt  a one-time code typed into boxes, handed on once
  widgets.mbt button, segmented control with a spring indicator
  theme.mbt   the theme (colours, corners, sizes) and the direction, in the Ctx
  response.mbt what happened to a widget (clicked, focused, changed…)
  semantics.mbt the semantics tree: roles, labels, states, actions
  focus.mbt   the keyboard's focus: Tab, roving groups, Enter and Space
  overlay.mbt layers over the page: stacked, dismissed, the focus trapped; Popper
  scene.mbt   paint: one flat array of 24-float instances
  app.mbt     frame loop, input dispatch, bench mode
src/kit     the components (Radix Primitives' set, docs/components.md): behaviour,
            semantics and a default look from the theme; the time they keep
src/kitdemo their gallery, light beside dark (APP=kitdemo, MBUI_SCREEN=<page>)
src/md      a small Markdown parser (blocks, inlines)
src/text    Unicode text segmentation (target independent, no host calls)
  grapheme.mbt   extended grapheme clusters, UAX #29 (caret, backspace)
  linebreak.mbt  line break opportunities, UAX #14 (wrapping)
  bidi.mbt       bidirectional levels and visual order, UAX #9
  tables.mbt     property tables, generated by scripts/gen_unicode.py
                 (bidi_tables.mbt by scripts/gen_bidi.py)
  *_conformance_test.mbt  Unicode's GraphemeBreakTest / LineBreakTest /
                 BidiCharacterTest
  testdata/corpus.txt  tricky strings for scripts/textdiff.sh
src/host    the platform boundary
  host_native.mbt / host_js.mbt   the same API over C and over JS
  apple_render.m  Metal renderer (macOS and iOS)
  apple_text.m    Core Text shaping and glyph atlas (macOS and iOS)
  mac_app.m       AppKit window, NSTextInputClient
  ios_app.m       UIKit view, UITextInput (built by scripts/ios.sh)
  win_render.cpp  Direct3D 11 renderer (WARP without a GPU)
  win_text.cpp    DirectWrite shaping, Direct2D glyphs into the same atlas
  win_app.c       Win32 window, per-monitor DPI, IMM32 input method
web/        browser host: WebGL2, canvas-2D text, hidden textarea for IME
src/demo    the demo: a chat screen with 10,000 messages
src/bench   a headless benchmark after nanoui's hill-climb (bench/README.md)
src/textdiff  the corpus drawn by mbui and by the platform's own text
            drawing, side by side (scripts/textdiff.sh)
```

Every renderer draws the same instances with the same shader (rounded rects
with borders, shadows, alpha-mask glyphs, color glyphs).

## Running (on a Mac with MoonBit and Xcode)

```sh
scripts/mac.sh build && scripts/mac.sh run      # macOS window
scripts/mac.sh script ime                       # scripted IME run, snapshots in out/ime
MBUI_BENCH=1 _build/native/release/build/demo/demo.exe   # scroll bench
scripts/bench.sh                                # offscreen benchmark scenes (bench/README.md)
scripts/web.sh build && scripts/web.sh test     # browser build + Playwright run
scripts/ios.sh build && scripts/ios.sh run      # iOS simulator
scripts/textdiff.sh mac web android             # mbui's text against the platform's own drawing:
                                                # out/textdiff/<host>/report.html (scripts/test.sh runs mac web)
```

Every native build compiles the one C file moonc generates for an app split into
units, in parallel (`scripts/mbc.py`, the splitter `scripts/csplit.py`): the
Android and iOS builds take only moonc's C from moon (`mbc.py gen`, its compile
for macOS left out) and compile it with their own compiler (`mbc.py compile`);
the macOS and Windows builds give moon a `cc`/`cl.exe` of ours that passes every
command through but that one (`mbc.py shim`/`wrap`). `moonbit_init` (every
global's initial value, run once) is a unit of its own at `-O0` (`/Od`).
The split is stable (`MBC_GROUP=stable`): moonc's made-up names (locals,
anonymous functions, layouts' offsets) are named by what they are, a package's
functions are a unit (a big package's in pieces by source file), and each unit
has only the declarations it uses, so an object made of the same text is kept
and a change compiles only the units whose functions it changed.
`MBC_SPLIT=0` compiles the file whole; `mbc.py check` compares the global
symbols of the whole and the split build, `scripts/mbc_test.py` tests both.

On Windows (Git Bash, MoonBit, MSVC from a Developer Command Prompt):

```sh
scripts/win.sh build && scripts/win.sh run      # Win32 window
scripts/win.sh script ime                       # scripted IME run, snapshots in out/ime
scripts/shots.sh windows                        # screenshot compared with goldens/windows.png
```

CI (`.github/workflows/windows.yml`) builds it on `windows-latest`, runs the
`shot` and `ime` scripts and compares the screenshot with the golden.
