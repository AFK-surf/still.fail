# 图层「挪位置只改偏移」需要宿主怎样认层——方案对比（草案，供审）

基于：mbui/layers-own-blocks `8f3b85633a`。现状：scene 每层自存块（层内坐标）、父层按引用拼帧，但每帧仍把所有块拷进一张平铺实例表、逐实例换算到窗口坐标再交宿主；宿主（apple_render.m、gles_render.h、Windows）每帧按 `count * MB_INST` 整表上传（GLES `glBufferData`，Windows `fill_vbuf` memcpy，Metal 同理）。所以挪动一层的 CPU 工作仍是 O(该层实例数)。

## 同行怎么做
- **Flutter**：`OffsetLayer`/`ClipRectLayer` 等组成层树；`PictureLayer` 的 DisplayList 录一次，合成时 `Preroll`/`Paint` 按层的变换与裁剪重放；重放本身仍按图元数提交 GPU 命令（Impeller 每帧重建命令缓冲），只有 raster cache 命中时整层当一张纹理贴（且平移要取整像素：`RasterCacheUtil::GetIntegralTransCTM`）。
- **Android HWUI**：`RenderNode` 存 DisplayList，`setTranslationX` 只改属性；RenderThread 每帧重放各节点 DisplayList，变换在 GPU 端（canvas 矩阵）完成，CPU 不改图元数据。
- **Chromium cc**：层的内容按 tile 栅格化留在 GPU；变换/裁剪/透明度放在 property trees，合成器每帧只算矩阵、提交 quad；挪动不重栅格化。

共同点：图元数据（或栅格结果）留在 GPU/渲染线程那边，挪动只改变换；没有谁每帧在 CPU 上把所有图元平移一遍。

## mbui 可选的三种结构
**A. 每层一段常驻实例缓冲 + 每层一次绘制（HWUI 式）**
- scene 交宿主的不再是平铺表，而是「层表」：每层 (id, 内容版本, 原点, 起始裁剪, 子层次序)；层内容变了才上传它那段（`glBufferSubData` / Metal `didModifyRange` / D3D `UpdateSubresource`）。
- 绘制按层发 draw call，偏移和起始裁剪走每次绘制的 uniform（GLES `glUniform`、Metal `setVertexBytes`、D3D 常量缓冲）。
- 代价（待原型实测，不预设）：一层的块被子层引用切成多段，须按「父段→子层→父段」画序提交，draw/pass 数至少是这些段数；宿主现按连续图片纹理、毛玻璃 capture、原生视图 hole 再分段与切换状态，会再增加 pass。

**B. 实例带层号 + 每帧一张小的层变换表（cc property tree 式）**
- 实例缓冲常驻，每个实例多一个槽存所属层号；每帧只上传层表（每层偏移、裁剪、透明度），着色器按层号查表。能否合成少数 draw call 取决于纹理切换和平台限制，待实测。
- 需要宿主侧管理实例缓冲的分配/回收（层块变长变短时搬移）。帧内次序（抬层、tops）若每帧按实例重建顺序表，就把 O(n) 搬回 CPU；次序必须按层/段表达，未改次序的移动不得逐实例生成或上传顺序表。
- 字形对齐像素放到着色器里（层内录未对齐位置，着色器按最终窗口位置取整），与本线已做的「合成时对齐」同一规则。

**C. 层栅格成纹理（Flutter raster cache / cc tiles 式）**
- 不变的层画进离屏纹理，挪动只贴纹理；文字和圆角在纹理边界、非整像素位置的画质要单独处理（Flutter 取整像素）；内存与毛玻璃取样交互最复杂。

## 我的初步倾向
B 最接近「每层自存、父层引用、挪位置只改偏移」，draw call 可能更少（待实测），但改动面最大（四个宿主的着色器、缓冲管理、帧内次序）；A 改动小、可先在一个宿主验证。建议先在 Metal（离屏渲染可在测试里比像素）做 A 的原型：同一 home fling 输入下对比整表上传 vs 按层上传的 CPU 时间、GPU 时间和像素，再决定是否走 B。

## Metal 原型 A 要纳入协议与对照的（审查提出）
- 层内多个可被引用打断的区段、纹理切换、形状带的段引用、遮罩抬升、毛玻璃后景、原生视图锚点。
- 实际 draw/pass 数、上传字节、CPU/GPU 时间；移动、裁剪/透明度、次序变化分别量。
- 层释放与重用、图集更新、GPU 在途缓冲的生命周期。
- 不同缩放、非整像素位移下的整帧像素、命中、宿主锚点对照。
- 未改次序的移动：核实没有逐实例生成/上传顺序表。

## 还缺的证据（不由本文给出）
- 各段真实用时（已请 fda1 按段量指令数；真实 CPU/GPU 时间要在设备或模拟器上量）。
- 毛玻璃取样、旧视图、原生视图锚点在按层绘制下的次序与正确性。

## 交接协议草稿（原型 A，Metal 先行；审查已允许与原型并行）
scene 每帧交给宿主的不再是整张实例表，而是三样东西：
1. **块的增量**：(块 id, 版本, 实例数, 实例数据) 只在块新录或变长变短时交；实例为层内坐标，字形存未对齐位置并带「基线 + 自身偏移」两个数（现在 scene_glyphs 记的那一对），每个实例带一个标记：它的裁剪是「层开始所在的裁剪」还是层内自己的（现在 scene_origin_put 用 inst_levels 判的 lv ≤ t）。形状带的段随块交，带的首段为块内下标。
2. **层表**（每帧全量，但只按层数）：每个可见层 (块 id, 窗口偏移, 开始所在的裁剪：clip/rc/rs 与 oclip/orc/ors 各 12 数, 透明度)。
3. **画序**：按层/段的列表 (块 id, 块内起止)，父段→子层→父段；毛玻璃 capture、原生 hole、抬层（over scrim）、tops 作为列表里的特殊项，不按实例展开。未改次序的帧画序不变，可整段沿用上帧的。

着色器（每段一次 draw，偏移和层裁剪走 setVertexBytes）：
- 位置 += 窗口偏移；字形：按最终窗口位置 × 缩放取整（与 glyph_set 同一规则：x 取整；y 先基线取整再加自身偏移取整）。
- 裁剪：标记为「开始所在」的实例直接用层裁剪；层内自己的裁剪 += 偏移后，与层裁剪**两者都测**（两个 SDF 取覆盖率乘积/最小值），不再在 CPU 上做 clip_cut_by 的「圆角取较圆者、外裁剪选切得最深者」近似。这会使像素与现路径在嵌套圆角交界处有细微差异——原型里单独量这一项，若需逐像素一致，再在着色器里实现与 clip_cut_by 等价的规则。
- 嵌套「自己原点」层：窗口偏移由 scene 累加好交给宿主（层表里已是窗口坐标），宿主不再嵌套。

原型的对照：同一 home fling 输入，整表路径（现行）vs 按层路径：完整帧像素（Metal 离屏）、损伤区、draw/pass 数、上传字节、CPU 时间（宿主侧）、GPU 时间；移动、裁剪/透明度、次序变化分开；层释放与 id 重用、图集更新、在途帧（3 个缓冲）的生命周期；缩放 2x/3x 与非整像素位移。
