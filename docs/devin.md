# Devin as a runtime

A station runs six runtimes: Claude Code, Codex, DeepSeek Harness (docs/dsh.md), Grok Build (docs/grok.md), Cursor (docs/cursor.md) and Devin, on the person's Devin account. Devin here is the Devin CLI ([docs.devin.ai/cli](https://docs.devin.ai/cli)), Cognition's local agent: the agent loop on the station, the models Cognition's (theirs, Anthropic's, OpenAI's, Google's and open ones). The driver is `station/src/agents/devin.ts`; the fake the tests run it against is `station/test/fake/devin.mjs`. Pinned against the Devin CLI 3000.11.92.

## How it is driven

- One `devin --config <profile home>/devin/config.json acp [--model M]` per session, under a runner whose id is the session key's, spoken to in ACP (JSON-RPC over stdio). The configuration is the station's: none of the person's other tools' rules, MCP servers and skills (`read_config_from` all off, their Devin Cloud's too), no updating itself (`auto_update: false`: the station updates it).
- `initialize`, then `authenticate` with the profile's key (`_meta.api_key`, the `windsurf_api_key` its sign-in left in `<profile home>/devin/data/devin/credentials.toml`), not whatever the CLI is signed in to on the machine. Custom variables bring their own `WINDSURF_API_KEY`.
- `session/new` (Devin names the session, two words: `foul-taxi`) or `session/load` for one it keeps, both with the station's tools as an HTTP MCP server (`mcpServers`, the session's bearer token in its headers) and a folder of the session's own as another workspace directory (`additionalDirectories`, below). `session/load` says the session's past again as updates before it answers: not a turn, not kept again. Then the `mode` config option is set to `bypass`: no approvals, as the other runtimes run here (a `session/request_permission` still asked is allowed for that call only).
- Devin keeps its sessions in a database of its own (`DEVIN_SESSIONS_DIR`, `<profile home>/devin/sessions/store`): in the shared sessions (agent-home.ts links `devin/sessions` for every profile that runs Devin), so any account takes a session on.
- A turn is `session/prompt`, answered when it ends: `stopReason` (`end_turn`; `cancelled` after `session/cancel`) or an error. A message for the running turn is another `session/prompt` given while it runs: Devin reads it at its next step (a command running then goes on) and answers it with the turn. One given just as the turn ended would be a turn of its own: the driver takes that turn up when its steps come (turnStarted) and ends it on that prompt's answer.
- The model's text and thoughts stream as `agent_message_chunk`/`agent_thought_chunk`, a call as `tool_call` then `tool_call_update`s (`LiveFromAcp`, agents/live.ts), named by Devin's `_meta["cognition.ai/inferenceToolName"]`: its own tools by their names (`exec`, `read`, `edit`…), an MCP server's as Claude Code names them (`mcp__stillfail__chat_post`). An MCP server's tools are listed by the model before it calls one (`mcp_list_tools`); the instructions say to call the station's directly. Devin's own notifications (`_cognition.ai/turn_stats`, `agent_stopped`, `thinking_complete`…) are not needed.
- A model is a family at a thinking level: Devin's variants are named `<family>-<level>` (`swe-2-high`, `claude-opus-5-5-xhigh`), and the station offers the family as the model and the level as its effort. The process is started with `--model <family>-<level>` (the family alone: its default level); another model or level between turns is the `model` config option (the option of that family) and `thought_level` (`retune`), not a new process.

## The station's instructions, memory and skills

A folder of the session's own, `<profile home>/devin/station/<hash of the key>/`, given to Devin as another workspace directory, which it reads as a project's root: the instructions as an always-on rule (`.devin/rules/stillfail.md`, `trigger: always_on`), the skills of the session's workspace linked in as `.devin/skills` (its memory is in the instructions, docs/multi-workspace.md). Nothing is written into the person's project. Devin still reads the machine's `~/.devin/rules`, `~/.config/devin/AGENTS.md` and `~/.agents/skills` (its HOME is the machine's, for the commands it runs).

## Which profiles run it

- **A Devin account** (Free, Pro, Max, Teams; Enterprise through its own sign-in): a `subscription` profile with `runtime: "devin"`. Signed in with `devin auth login --force-manual-token-flow` with `XDG_DATA_HOME` the profile's `devin/data` (LoginManager, accounts/login.ts): it prints a page at app.devin.ai; after signing in there, the page shows a code the person pastes back, as Claude's. It reads the code only from a terminal: the command runs in one (`platform.terminal`, the system's `script`), 1000 columns wide so that its page (with an OSC 8 link around it) is on one line; on Windows, which has none of these, the sign-in is refused. Checked with `devin auth status` (whether signed in, and the account's email, noted in `devin/account.json`) and `devin models list --format json` (the models, a family each at its levels: the name most of its variants are a level of; its variants of another kind (`glm-5-2-1m`, `-thinking`), the faster and prioritised ones (billed apart) and Fusion's hundreds of pairs of a model and a sidekick left out). Devin says no plan usage to a program: the allowance is `unsupported`. Not lent to other stations yet: sharing one is refused.
- Custom variables: Devin's own (`WINDSURF_API_KEY`).

## Installed

By its own installer (`curl -fsSL https://cli.devin.ai/install.sh | bash`; on Windows its install.ps1), into `~/.local/bin/devin`, a link to `~/.local/share/devin/cli/_versions/<version>/bin/devin`. Its latest version is its manifest's (`https://static.devin.ai/cli/current/manifest.json`); updated by running the installer again. The station runs the installer without its last line, `devin setup` (a sign-in of the machine's own that wants a terminal: without one it ends "Login canceled" and the install with it); `devin update` wants a terminal too (without one it ends at once, nothing done).

## History and usage

Devin's store is not read: the driver keeps the transcript itself, `<profile home>/devin/sessions/<id>.jsonl`, in Cursor's lines (docs/cursor.md): `user` (the prompt, or a message steered in), `assistant` and `thinking` (whole, as they were said in pieces), `tool` (a call and what it gave back), `usage` and `end`. A turn's `usage` sums the counts Devin says after each model call (`usage_update`, said twice for each call: counted once), input apart from the cache's read, with the context the turn ended with (`used`) and the model's window (`size`). `read/transcript.ts`, usage/counter.ts and sessions/live.ts read it as Cursor's.
