# 消息列表里的动效

聊天的消息列表（电脑和手机网页共用 `web/src/Chat.tsx` 的行）跟随到底：停在最底下时，新东西来了面板会滑过去（`virtual/list.tsx`）。列表里什么东西一变，就会和这个滚动互相影响。下面的规则就是为此定的，改动效之前先读。

## 行高本身是会动的量（2026-10-30 用户：「那些会变长或缩短的消息列表内容的动效协同起来的效果，需要系统性设计一下」）

之前的做法是排版一帧到位，再用整个列表滑一下、新行淡入上浮、离开的行留副本、排队一次只动一件、「在屏幕上答完的不收、看不见了才收」这几层去盖。每层都在给上一层打补丁，「看不见才收」还靠「上一帧有没有重新搭界面」判断，界面静止跳过重搭时会在眼前收掉。现在换成一条规则：

- **每一行此刻有多高，是一个随起因过渡的值。** 起因由列表自己从每一行的身份（key）和内容版本认出来，页面不用说：新出现的 key 是进来（从 0 长到它的高度），不见了的 key 是离开（缩到 0；离开前一直留在列表里、排在它原来跟着的那行后面，列表的路走完才拿掉），同一个 key 版本变了是内容变了（从当时的高度到新的高度）。都用移动的曲线（`Move`，`row_size_ms`，300 ms；还没按距离定时长），起因一来就动，不等。
- **原地进出的行：内容摆在位置正中，两头裁，裁口淡出**（2026-10-31 用户：「有一些是凭空出现的，有一些是凭空消失的」「这样会影响速度吧，你要不两头裁呢？再加上淡化的边缘」）。没有飞行带它来的行（`ListRows::enter`）和离开的行（`ListRows::leave`）：列表把内容（行顶上和上一行之间的间距不算，间距跟着一起开合：`enter`/`leave` 的 `lead`）排在这一行此刻那块地方的正中（点、找、画都在那里），上下两头被这块地方裁掉，裁口往里淡出（最多 24 点，`cut_soft_most`，不超过露出部分的一半），整体透明度和大小跟着这块地方开了多少走：高度一边收、内容跟着一起缩（开了几成就是几成大），透明度更快：缩到一半时已经完全看不见，后半段看不到它变得很小（`row_held_look`；2026-10-31 用户：「感觉缩到 90% 不太够」「试试高度压缩过程中持续缩小」，缩到零后：「感觉缩太多也不行，或者尽量在缩到 50% 左右的时候就变成完全看不见了」「item 除了缩小不是还有个透明度吗」；之前是 96% 到 100%）；离开就是倒着放。在卡片里的行（设置页、文件页）只有内容缩放淡出，卡片的底只跟着开合（「背景被你当成 item 处理了」：`ListRows::enter`/`leave` 标出的节点，`room_held`）。行里的东西收起展开（卡片选项、「忽略」、要人处理的卡片：`under_post`）同样在它那块地方正中、两头裁、裁口淡出（`@motion.reveal` 的 `middle`）。之前试过「先淡完再收」，多等 150 ms，被换掉。
- **页面只给 key 和版本。** 不写「这种行怎么动」「什么时候要重搭」：行搭好就留着，排版时按 key 查此刻该多高；列表认出的变化是被跟踪的值，排版和读它的行在它变的那一刻被告知，不靠「在动就整行重搭」。
- **每一行的位置就是它上面各行此刻高度之和。** 行和行永远首尾相接，不会叠字、不会有空洞，不需要副本，也不需要排队：几件事同时发生就一起动，合起来是一次连贯的移动。
- **同时在动的行走同一条路**（2026-10-30 用户：「在有决策卡片的时候发消息，整个消息列表会频繁来回移动」）：列表只有一条路，从最近一个起因那一刻出发，到给过的最晚的终点（发出去的消息跟飞行一样长）结束；路上每一行离它该有的高度还差多少，每一刻都剩同样的比例。所以上面的行（它们的位置是下面各行之和）只往一个方向走。之前卡片收起 300 ms、你的消息长出 520 ms，各走各的曲线，上面的行先被收起拉下去、再被消息推上来。新的起因来了，在动的行从当时的高度、**带着当时的速度**一起接着走到新终点（`@ui.move_path`），不从静止重新起步——从静止起步时，速度会在新起因那一帧掉下去再涨回来（2026-10-30 用户：「还是会有顿挫」）。行里自己会改高度的东西（卡片选项收起：`under_post`）在列表的这条路上走（`Ctx::row_way`），不另起一条；列表只补「变的那一刻差出来的」高度，行里自己动的不再叠一层。
- **谁不动只看列表自己的规则。** 停在底部时底部不动，变化往上推或往下落；往上翻着看时，正在看的那一行不动，它上面的变化往上走、下面的往下走。往上翻着看时也一样按上面这些动，不再「没跟着底部就一帧到位」（2026-10-31 用户：「有一些是凭空出现的，有一些是凭空消失的」）；只是从头像吐出来的回复不吐，原地进来。
- **内容变了才算「变了」**：消息的字、附件、时间出现、卡片答完、发送状态这类（`shown_sign`）；core 把同样的东西再给一遍不算。一行还在进来时内容又变了（例如刚发出去的消息被 core 接手），接着按「进来」走到新的高度，不另起一段。没有起因的高度变化（窗口变宽、图片后来才知道尺寸）当场到位；正在过渡中的行目标变了，从当前高度接着走过去。
- **不是这次才来的不算「进来」**：打开对话时已有的、离开期间漏掉后补进来的消息，当场在位。
- **自己发的消息一个身份到底**：从按下发送起就用发送时的 key，core 收进发件箱、变成消息都还是这一行，不会被当成「一行走、另一行来」。
- 答完、忽略的卡片当场收起（选项淡出、收起的地方淡入「谁选了什么」），和你的回复进来同一时刻开始，合成一次移动；不再有「看不见才收」。卡片「已答」由 core 在你点下时就生效（`decisions.ts`），不等 station 回来。
- 飞的东西（发出去的字、头像吐出的消息）对准目标行此刻排出来的位置，落地时正好对上；目标行进来的时长和飞行一样长。
- **发出去的字离开输入框那一刻，消息行和输入框让出的位置一起动**（2026-10-30 用户看过改前改后同意）：字先在输入框里停一下（飞行的四分之一），输入框为它们留着高度；之前消息行一发出就长、输入框之后按自己的曲线收，上面的行先上去再掉回来。现在列表从字离开那一刻起（`ListRows::rows` 的 `from`）让消息行长出来、底部那段留白（Foot 行，`composer_foot_room`）收到输入框落定的高度，输入框的底和留白也在同一刻、同样长地收（`sent_down_of`）；这段等待里别的变化（卡片收起、一行离开）也从这一刻一起走。
- **动的时候不重搭**：行的淡入淡出、活动行的长出在画的时候读（`Ctx::look_by`），行高在排版时读；飞行在搭的时候只读气泡里字的断行和大小（`Ctx::words_shape_of`），位置在画的时候读，所以气泡跟着列表挪不会让整帧重搭。

mbui：框架 `ui/list_size.mbt`（`ListRows::rows` 从 key 和版本认出 `RowSize::Comes/Goes/Changed`，`Ctx::list(sized=)` 排版时按 key 查高度，`row_gone`），对话列表 `sfbase/chat_list.mbt` 只给 key 和版本（`shown_rows`、`shown_sign`），`sfpages/chat_list.mbt` 对每行调 `ListRows::enter` / `leave`（agent 干活那行进来、停留 600 ms 后离开也走这一条；自己发的消息飞进来、agent 的回复从头像吐出来的不走 `enter`）。对话列表（首页、侧栏 `sfpages/sidebar.mbt`）2026-10-31 起也走这一套：一行（或一天的标题）进来、离开同上；一个对话被顶到前面（`ListRows::rows` 的 `moves`），在原处留一个副本收起、在新位置撑开，不从别的行上面滑过（用户试过滑过去：「移动会有遮盖问题」「原地缩下去再从目标点挤出来更合理」）；列表等待后第一次有行、或上一帧没画出来（回到首页、翻到这一页），照原样显示、不补播。网页（`listQueue.ts`、`settling.tsx`、`virtual/list.tsx`）还是下面的旧做法，下一步按同一套改。

## 检查：行不许顿挫（`ui/rows_steady.mbt`）

所有测试和回放画出的每一帧，列表里看得见的行：不许三帧内先往一边又退回（各 ≥2 点）；某帧的速度不许偏离前后两帧的平均超过 3 点/帧且超过前后较快者的一半（突跳、中途停住、从静止猛起步都算）。用户手拖、app 一下挪到别处的那帧、列表出现的头 100 ms 不算。现有的按文件记数（`rows_steady_known`），只许减（2026-10-30 用户：「这么一个一个找合理吗？」「二阶不平滑」）。

## 两类动效

**只改透明度和位置的**：不碰行高，滚动也不受影响。

- 进场统一用 `motion.ts` 的 `ENTER` / `ENTER_FROM`：从下方 6px 处淡入，220ms 缓出。新消息的 `[data-enter]`、「忽略」「留着/归档」出现时，都是这一种。
- 离场统一用 `LEAVE` / `LEAVE_TO`：在原处放一个副本，缩小到 0.9 并淡出，200ms。和侧栏的行离开一样（`listMotion.ts`）。

**会改变行高的**：「忽略」「留着/归档」出现（`settling.tsx` 的 `Settles`）。答完收起不在屏幕上播（见上），所以没有收起的动画。出现时：

1. grid 的间距跟着一起开。grid 的行高最小是 0，单靠负 margin 抵不掉上面的间距，所以由前一个元素先把这段间距让出来，展开时再还回去。
2. 框的高度和面板的滚动用同一规律、从同一帧开始走：`motion.ts` 的 `GLIDE_TAU`（每帧走剩下距离的一部分，约 250ms 走完 90%），`GLIDE_MS` / `GLIDE_EASE` 是同一规律写成固定时长的动画。这样上面和下面的东西各自只朝一个方向动。活动行在上面的东西变化时会保持在原位，它的滑动也用同一规律（`glider`）。

### 例外

- agent 的消息从头像里吐出来（`useEmissions`）：整行高度一次到位，内容靠合成器从头像角展开，再配合头像的飞行。这样设计是为了长消息展开时不用每帧重新排版。等待中的消息不占位置，也不显示；列表事先就知道它不占位置（`Item.exact`），不按估计的高度先挪一下下面的东西。
- 活动行的出现和消失（`Activity`）：用 Motion 动 `grid-template-rows`。列表会为离开的临时行留出空间（`model.ts` 的 `held`）。新出现的活动行在队列里排在刚发出的消息后面，等它落下、列表到位再出现。

## 检查

`test/browser/list-settle.mjs` 在官网 demo 的聊天里（假 core，用真页面）分别在宽屏和手机尺寸下各跑一遍，场景有：发消息、发消息后 agent 立刻开始干活、agent 回消息、比屏幕还高的回复、回复决策、点选项、忽略、留着/归档的出现和消失、活动行的出现和消失、agent 消息从头像吐出。每一帧都在列表把滚动摆正之后、绘制之前取样，下面任何一条出现就算失败：

- 有一行在三帧之内先往一个方向移、再往回移，两次都超过 2px；
- 自己的消息还在从输入框飞向列表时，新出现的活动行已经显示出来（应该等消息落下后，出现在它下面）；
- 结束时面板没有停在底部（比屏幕还高的回复除外，它是从顶部开始读的）。

它不检查时长：掉帧只会让样本变少，不会改变东西移动的方向。瞬移（一帧里走了 24px 以上、速度是前后帧三倍以上）只打印出来不判失败：慢机器上一帧拖长，正常滑动的一步也会变大；加 `JUMPS=1` 才按失败算，本机查问题时用。

完整检查（`scripts/check.sh full`）里，它跟在 stories.mjs 后面，在同一步依次跑。本机跑的方法：

```
PLAYWRIGHT_MODULE=<playwright-core 的 index.mjs> PLAYWRIGHT_CHANNEL=chrome node test/browser/list-settle.mjs
```

加 `ONLY=<场景>` 只跑一个场景，加 `SHOTS=<目录>` 会把每个场景的逐帧数据存下来。
