# 个人锁

> 2026-11-05 左子健定：「不再有 workspace 锁，只有个人锁，所谓的 workspace 锁其实就是管理员的个人锁」。
>
> 新架构已接入账号存储、规则、station 放行，以及客户端的设备配对、手机授权签名和设置页面；workspace 名单迁到个人锁仍按下方 B–D 分阶段进行。

## 目标

只有个人锁一种锁，它是唯一的信任根。

- **个人锁**：一个人有哪些设备。一条带哈希链的签名记录，跟着账号走，只有这个人已有的设备能改。owner、admin 和 cloud 都改不了。
- **workspace 名单**：谁是成员（角色、他的个人锁 ID）、哪些 station 和 gateway 算数、cloud 公钥。由 owner 和 admin 用个人钥匙签，保留哈希链，防回滚和分叉。名单里不再有设备。
- **设备连 station**：出示自己的个人锁，station 按「名单钉的个人锁 → 这台设备在锁里」验证。
- **不开名单的 workspace**：成员和 station 信 cloud，手机授权和个人密钥库仍受个人锁保护。

## 现在做到哪

| | 状态 |
|---|---|
| 个人锁本身、面对面加设备 | 已做 |
| 手机授权签名、手机验签 | 已做 |
| A：个人锁进 `rules/` 和 Tamarin；workspace 锁认识 `person` 条目；station 按个人锁放行 | 已做，还没有设备写 `person` 条目 |
| B：stable 带上 A 后，app 自动绑定，个人锁加设备后各 workspace 都放行 | 没做 |
| C：绑定的人不再接受设备条目，新成员由 admin 面对面钉个人锁 ID | 没做 |
| D：密钥库迁到个人锁 | 没做，密钥库仍依赖 workspace 锁 |

旧 station 拒收不认识的条目类型（`unknown entry kind`），之后整条链都接不上，所以 B 必须等 stable 的 station 都带上 A。

## 绑定（`person` 条目）

现有成员的设备可以签一条 `person {sub, person}`（`person` 是个人锁 genesis 的哈希），就等于说「这个人的个人锁是这条」。规则只接受 workspace 锁认作该成员本人的设备或 passkey 的签名（`role.binds`）；管理员自己的签名不能直接替他绑定。成员被移除时绑定也一起清掉。

首设备有既有的信任边界：成员还没有本人签名设备时，owner 或 admin 加入的第一台会被规则当作本人的。正常流程让双方面对面核对安全码；链规则本身不证明这次核对发生过，恶意管理员若把自己控制的设备作为此成员的第一台，就能用那台设备签绑定。不能把「规则只认本人的设备」解读为已经防住恶意管理员伪造首设备；C 阶段还需用面对面证明钉住新成员的个人锁 ID。

绑定之后，新设备即使不在 workspace 锁里，只要在绑定的个人锁里也能放行。A 阶段原有的 workspace 设备条目仍然有效：如果同一设备也在 workspace 锁里，只从个人锁移除它不能撤销这条已有的准入路径，还须从 workspace 锁移除。彻底切到个人锁属于后面的 C 阶段；还没绑定的人继续按设备条目，所以没有所有人同时切换的时刻。

station 将验证过的最长链保存在本机；重启或进程交接后，听到的旧链不能覆盖它。设备首次经个人锁连接时，station 用自身密钥向 cloud 取当前链，验签并按 workspace 绑定的 genesis 核对，不以设备带来的旧链证明自己仍在锁中。长链由 station 取得，不塞进连接的首行；验签和链比较在单独的工作线程里进行，等待结果期间再次核对在线状态、成员、绑定和记录版本。收到新的个人锁通知时，按个人锁放行的既有连接先关闭，设备重新连接后按新记录检查。cloud 向在线 station 推送变更，并将待发通知和记录一起保存：保存之后发送之前中断，会再次尝试。station 检测到推送通道断开后，依靠个人锁放行的连接关闭，恢复后重新查当前链；半开连接靠周期心跳发现。链与 cloud 都不能证明一个从未见过撤销的 station 一定拿到了最新记录：若 cloud 本身恶意隐瞒更新，仍有这个信任边界。

## 记录

条目和 workspace 锁同形（`lock-form.ts` 的哈希、Ed25519 签名），`ws` 是 `person:<sub>`，所以签名挪不到别的锁上。

| kind | body | 谁能签 |
|---|---|---|
| `genesis` | `{sub, device: {key, id, label}}` | 这台设备自己 |
| `device` | `{key, id, label}` | 锁里的设备 |
| `device.remove` | `{key}` | 锁里的设备，不能移除最后一个签名 key；移除该 key 对应 base 下的所有 key |

`key` 是设备的个人钥匙，`id` 是它的 iroh 基础密钥（面对面批准时拨它）。
历史记录若用多个签名 key 指向同一个 base，撤销其中一个会同时撤销该 base 的所有 key，避免已移除的设备继续冒用另一个 key 进入。若那是锁里仅剩的物理设备，撤销后没有 key 能继续签名，需要通过新建个人锁恢复。

- **钥匙**：`personal-signer`，每台 app 设备一把，`user: true` 封存：每次用都要过生物识别或屏幕锁。这和 `lock-signer` 不同，后者不问人。网页版没有：页面代码是 cloud 发的。
- **cloud**：`GET/POST /v1/me/personal-lock`，存在账号自己的对象里（`cloud/src/personal-lock.ts`）。长记录分段保存，旧版单值记录在下一次追加时迁移。已有 genesis 的记录只能在已接受前缀后追加，重传旧记录不会截短，分叉和旧 genesis 重放会被拒绝；并发写同一位置也只有一条能接受。只偷到登录态写不进已有的锁；但从不同 `genesis` 开始的新链它会收（设备全丢时要用），被盗登录态因此仍可触发重建并造成拒绝服务。恢复已钉住的长链时，通过 `POST /v1/me/personal-lock/append` 按 UTF-8 字节分段（每次最多 256 KiB）并带当前头作为前置条件，避免覆盖另一台设备刚新建的锁；遇到账号请求限额按 cloud 的等待时间重试。旧 cloud 不认识这个路径，恢复会失败等待升级，不能退回无条件写入。
- **钉住**：设备只信自己钉住的那条链。cloud 给的链只有在延长钉住的链时才接受；不一样就是 `replaced`，手机继续按原来钉住的验，这台设备不再签任何东西，直到人确认。发现尚未钉住的有效链后会把这一发现保存在本机，较早、空或无效的回复和离线重启都不会清除；明确忘记、重新加入或新建时才处理。旧版客户端不读取这份记录，不能依赖降级后的客户端保留这一保护。
- **保存失败**：新链已经验证、但写入本机失败时，运行中的客户端保留新链（包括其中的撤销），暂停用该账号签授权或出借手机，直到新链写入成功；发现另一条链的记录也按此处理，重试不依赖 cloud 在线。若进程在写入始终失败时退出，重启后只有旧的本地记录，离线时无法知道只存在于上次内存中的撤销或另一条链；联网刷新后才能再次发现它。本地锁、另一条链的记录或钥匙身份读取失败、内容损坏时，不能当作没有锁而自动新建。
- **确认的恢复**：人明确加入或重建时，先在本机记下这次选择，再换钉住的链、清除已接受的替代记录；其中任一步未完成都暂停签名和出借，重启后可继续。已验证的加入结果可离线续存；重建回复丢失时先核对 cloud，只有仍是人所见的旧链时才带旧链头原子重试，不能覆盖期间新出现的链。忘记也先记录意图，清理中断不会把之前待确认的选择重新钉住。旧版客户端不读取这些待完成记录，降级不能保留这些保护。

## 开启和加设备

1. 没开个人锁不能批准（2026-11-06，左子健：「没开个人锁不让批准你他妈让它开个人锁啊」）：申请卡片上没有「允许」，只有「开启个人锁」，点了到 设置 › 安全 › 个人锁。这是个人锁自己的事，卡片上不放输入框。
2. 个人锁页：这个人还没有锁，点「开启个人锁」，这台设备生成钥匙，签 `genesis`，交给 cloud，自己钉住。自动首次创建通过带空链前置条件的 `/append` 原子提交；两台设备同时创建时只有一个能成功，旧 cloud 不支持时等待升级，不退回无条件重建。发送前先保存本机签过的待确认条目：若 cloud 已收下而回复丢失，重启后只有取回完全相同的有效链才自动钉住，也保留其后续撤销；离线或其他链不能凭待确认条目签名，明确忘记会清掉它。已经在别的设备开过，读 cloud 上的锁，拨上面每台设备（沿用 `views/pair.ts`，`hello` 带 `personal: {sub, key}`，`workspaces` 为空）。
3. 锁里的设备先过一次生物识别，再显示安全码；新设备输入，CPace 证明（`pair.ts`），输完不再验证。一个码对两台设备共同登录、且显示码那台在锁里的账号都生效：逐个账号签 `device`，把各条链经这条已证明的连接交给新设备钉住。两个账号的锁分别由这两台各自先建时，还要反过来再输一次（2026-11-06 左子健就是这样，这种情况先不做）。
4. 新设备不能只凭 cloud 的话把自己钉上：cloud 可以塞一条假链，但它拿不到人眼看到的安全码。

**设备全丢**：新设备点「新建个人锁」，签新的 `genesis`，提交时要求 cloud 仍是人看到的链；若期间变了，先显示新的状态，不能静默覆盖。别的设备显示 `replaced`，人确认后才改用；手机上的授权都要重新批。旧 cloud 不支持前置条件时需先升级，不能退回无条件重建。

## 手机授权

- **批准**：`adb.decide` 允许时，core 签 `{v, sub, station, request, session, chat, scope, exp}`（标签 `stillfail-phone-grant/1`），随决定交给 station。station 只带着，不读。
- **手机验**：`adb.ts` 的 `#holds`：签名的钥匙在钉住的锁里、内容和 station 说的这条授权一一对得上、没过期、没在这台手机上收回过，才算数。`wanted()` 只看算数的。
- **到期**：手机按签名里的 `exp` 自己停止出借，不需要 station 说。
- **收回**：这台手机在设备上记住整个 station 与对话的收回（`adb-revoked`），也记住当时已知的请求 ID；station 之后才拿出同一对话的其他旧签名，也不能使它重新出借。旧签名没有可信签发顺序，另一台受信设备后来批准的签名同样须在这台手机的共享调试页明确允许一次；这次只放行确认时的那份有效签名，并把期限限制在当时看到的较早截止和本机最长授权以内。有效签名可离线确认；未签的旧授权须能联系支持签名的 station。手机上在对话卡片批准新请求时，核对请求与所显示的对话相同后签名并放行该签名；无法核对对话的旧客户端不能用这条路径绕开收回。若收回时无法确认那行属于哪个对话，则保守地暂停该 station 的授权，每次仍可在手机上逐条允许。

  收回记录不信 station 提供的期限，因而会随收回次数增长。启动时须先读完记录才能出借；读取损坏或保存失败时暂停出借，在共享调试页可重试。保存成功前进程若退出，未写入的收回可能丢失；升级前仅按请求 ID 保存的旧收回没有对话身份，无法追补之前被隐藏的其他请求，旧版已清掉的记录也不能恢复。旧客户端不认识按对话的记录，降级不能保留这一保护。在别的设备上收回仍靠 station 转告；改成可验证的跨设备收回之前，不老实的 station 可以隐瞒这次操作。

- **更新前批的授权**：没有签名，手机不出借。个人锁页和共享调试页显示「N 个对话的授权需要确认」，点一下，只验证一次，全部签好（`adb.personalConfirm`，station 的 `sign`），不用让 agent 重新申请。确认时按手机时钟限制期限：一小时授权最多再过一小时，对话授权最多再过三十天；原期限更早则保留原期限。显示、保存和出借均不晚于签名的期限。已签过的旧授权没有签发时刻，无法据此证明它签署时符合此上限。
- **旧 station**：`grants` 的回答没有 `signs: true`，它会丢掉签名，卡片直接说要先更新这台 station。
- **多个账号**：每个账号一条锁，`adbShare.personal` 是列表；申请按它所在 workspace 的账号算。

## 挡得住什么

| 攻击 | 结果 |
|---|---|
| 账号或网页登录态被盗，点批准 | 批不了：没有钥匙 |
| 被盗的账号登录新设备 | 加不进锁：要已有设备显示的安全码 |
| cloud 被攻破，改锁或给假链 | 钉住的设备不跟 |
| station 数据库被改、station 被攻破，说「有授权」 | 手机验签不过，不出借 |
| workspace admin 冒充你批准 | 已确认的个人锁里没有他的 key 时，手机授权验签不通过；首设备交接仍有上面所述的信任边界 |

挡不住：

- **活跃授权期间的同机 agent**：手机分不清连接来自哪个对话，这一层只有 `station/src/adb/door.ts` 按进程区分，同一系统用户下存心绕过的 agent 能绕开。要彻底隔离得每个 session 独立系统用户或沙箱。
- **扣着不发**：cloud 可以不把 `device.remove` 发给手机，已丢的设备在手机收到前还能批。
- **第一台设备**：手机第一次开启或加入之前没有东西可钉。

## 兼容

- 旧 station：不带 `signed`，新手机不出借，等 station 更新后重新批。
- 旧 app：批准不带签名；旧手机照旧按 station 的话出借，升级后就不再认这些授权。
- 升级之前批的授权都没有签名，都要重新批。
