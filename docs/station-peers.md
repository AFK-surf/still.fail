# Station peers and remote tasks

Stations in the same workspace can discover each other and call named services over iroh. The first service runs shell tasks and transfers files. It has no dependency on a machine name, toolchain, repository, model or SSH. A command runs in a fresh task directory on the destination as its OS user; this is **not a sandbox**.

## Permission and compatibility

Any station of the workspace may run tasks on another; nothing is configured. Its agents could already open a chat there (`chat_create`) whose agent runs the same commands, so a separate opt-in protected nothing. It does not forward a person's admin credential or open the target's management APIs. Request metadata records the source station, source session and its creator (`requestedBy`, asserted by the source station, not an independently verified user identity).

Stations before this change still require the source station's public key in their `config.json` (`{"remoteTasks":{"allow":[...]}}`) and refuse tasks without it; newer stations ignore the field.

Cloud sends an additional `peers` field on station presence state frames. A station that pinned its workspace's lock ([workspace-lock.md](workspace-lock.md)) takes only the stations the lock names too: the cloud can leave one out, not add one. Enrollment, removal, movement and renaming update the workspace roster. A peer's iroh public key must match that roster; the request must name the same workspace. New calls fail closed before a first roster arrives, once the control-plane connection has been gone for a minute (`ROSTER_GRACE_MS`, presence.ts: the cloud closes it now and then and it is back within seconds; every call in those seconds was refused), or at once when the station is removed. Removal from the workspace stops that station's running tasks on the next check (every five seconds). Losing connectivity alone does not kill running commands.

Deploy cloud first, then the stations that participate. Old stations ignore the new field; an old cloud provides no roster, so peer calls remain disabled. Existing member connections and existing local job tools keep their behavior. No database version change or data migration is required.

## Agent tools

- `station_list {}` returns the workspace's registered stations, whether the roster is current, and for each how busy it is now (`load`, one line; see "Load"). `station_list {station}` connects to one and returns its protocol, OS, architecture, whether it accepts tasks, file limits and its `load` in full, with that line as `summary`.
- `station_task {station, action:"prepare", key, name, command}` records the task specification and creates its directory. Pick a stable key for one execution. Preparing that key with a different specification is refused.
- `station_task {…, action:"prepare", dir, back}` (both optional): `dir` is an absolute path of a directory on the source machine; every start syncs it into a mirror on the target first and runs the command there (see "Directories"). `back` lists paths relative to where the command runs, downloaded when it ends into `station-back/<key>/` of the source session's workspace.
- `station_file {station, key, direction:"upload", local, path}` uploads a local session file into a relative path in that task directory. Finish uploading before starting.
- `station_task {station, action:"start", key}` starts the prepared command. A retry with the same key returns the original job; it never deliberately starts another copy.
- `station_task {station, action:"get"|"log"|"stop", key}` reads status, tails logs or cancels the task. `action:"list"` lists this source session's tasks on the target, including prepared tasks.
- `station_file {station, key, direction:"download", path, local}` downloads an artifact after the task finishes. It creates a new file inside the source session workspace and does not overwrite existing files. The agent can attach it to its original conversation with `chat_post`.

A file goes whole after one request (an upload) or one answer (a download), its bytes as they are read (see "Transport"); to and from a station from before, in 256 KiB chunks of base64. Up to 1 GiB per file. Binary files work. Paths cannot escape the task directory and transfers refuse symbolic links. Inputs cannot be written through the transfer API after execution starts. An interrupted upload can be repeated; an incomplete upload blocks start. Downloads publish the final filename only once the transfer succeeds. For a working directory (a checkout with local changes), give `dir` instead of uploading it.

## Load

Agents pick the station for a task by how busy it is; there are no locks between them. `describe` answers `load` (`station/src/jobs/load.ts`): `os`, `arch`, `cpus`, `cpuModel`; `cpuBusy` (`share` 0–1 over `seconds`, about the last minute, from CPU ticks the station notes every 15 s; `seconds` null when it has only the moment before); `loadAvg` (1/5/15 min, null on Windows); `memory` (`totalBytes`, `availableBytes`); `disk` (the volume of the data directory, where tasks run); `gpus` (Apple Silicon: the chip and its GPU cores from `ioreg`; NVIDIA through `nvidia-smi`, its memory and how busy; null when none is known); `running` (`remoteTasks` from other stations, `jobs`, `services`, agent `turns`); `relay` (`home`, and `ping`: a ping to the home relay, timed on a warm connection every 30 s by `mesh/relays.ts`); `checkedAt`. The machine figures are GET /host's (`api/host.ts`, the same ten-second cache the station page uses). Measuring waits at most 1 s; past that, or on an error, `load` is `{unavailable}`.

`station_list {}` asks every listed station at once (this one answers itself, `here: true`); one that has not answered within 2 s is listed with `offline`, one that refused with `refused`, and the list never waits longer. A station from before this answers `describe` without `load`: its load is "unknown (older station)".

## Directories

A task prepared with `dir` runs in a mirror of that directory, `<name>` in the session's directory on the target (its last path component; with part of a hash when another directory of the session has that name there). The prepare answer names it (`dir`). On each start, before the command, the source brings the mirror up to date (`station_task` start's answer has `sync`: files, contents sent and their bytes raw and compressed, requests, written, removed, skipped, ms). Code: `station/src/jobs/dirsync.ts`.

- Which files: in a Git work tree, `git ls-files -co --exclude-standard` (tracked, plus untracked files not ignored), so `node_modules`, `target`, `dist` and other ignored output stay home. Elsewhere (or in a directory its work tree ignores) every file except directories named `.git`, `.hg`, `.svn`, `.jj`, `node_modules`, `target`, `dist`, `build`, `.gradle`, `.next`, `.turbo`, `.cache`, `__pycache__`, `.venv`, and `.DS_Store`. `.git` is not synced; submodules and nested repositories are skipped. A symbolic link is synced as a link when its target stays inside the directory; a link leading out (absolute, or `..` past the top) is skipped and listed in `skipped`. Files over 1 GiB are skipped; more than 200,000 files are refused.
- Comparing: a file's id is its Git blob id (sha1 of `blob <size>\0` and the bytes). A clean tracked file the mirror already has takes it from the index; modified, untracked and non-Git files, and clean ones that would be sent, are hashed (with Git filters or eol conversion — a `.bat` checked out with CRLF, LFS — the bytes on disk are not what the index names). The target keeps a manifest of what it wrote into the mirror (path → id, mode, and the size/mtime/inode it left) and reports what is there now; a file a command changed is hashed again, so the next sync puts it back.
- Transfer: `sync.begin` (refused while another task of the session runs in that mirror), `sync.manifest` pages, `sync.put` (pieces of at most 512 KiB of the contents the mirror has nowhere — a renamed or copied file is copied there, not sent — at most 16 MiB of them per request, packed with zstd, after the request; to a station from before, base64 in it, at most 720 KiB, within its transport's 1 MiB message), `sync.commit` pages with the final one applying. Each content is checked against its id when its last piece arrives. A station sends its bulk requests (every sync's `sync.put`, `station_file` files, what a task brings back) one at a time, in the order they come: everything it sends another station waits in one queue (a relay's, first in, first out), and several syncs pushing at once once kept members' devices from connecting for ten minutes, their handshakes queued ten seconds behind the contents (2026-10-19). A file in one stream keeps no more than that: QUIC's flow control lets at most a stream's window (about 1.25 MB) go ahead of what the other end read.
- Answering: a start answers within 40 s (`SYNC_ANSWER_MS`) whether its sync has ended or not; one that has not answers `{syncing: true, note}` and the sync goes on. A start of the same task asked again waits on that sync (or takes what it did, ended within ten minutes) instead of beginning another, which the target would take for a new one and end the first; syncs of other tasks into the same mirror begin after it.
- Writing: every new content is made beside the mirror first (temp file, mode 0644/0755 from the exec bit, or a link), then files that left the set are removed (and directories left empty by that), then the new ones are renamed into place. Files the source does not name — build output, `node_modules`, anything a task made — are never touched, and an unchanged file keeps its mtime, so incremental builds see exactly what changed. A path whose parent is a symbolic link, or a non-empty directory where a file should go, stops the commit with an error; the manifest records what was done.
- Cleanup: a mirror no task of the session has run in, synced or ended in for 24 hours (`MIRROR_IDLE_MS`) is removed by the target, with everything its tasks made in it (build output, recordings); the next start syncs it from nothing. When the disk holding the station's data has less than 20 GiB free (`DISK_LOW_BYTES` in `ops/disk.ts`, looked at by the station every five minutes), mirrors go sooner, the longest unused first, until there is that much again; one a task runs in or a sync is writing to, or one used within the hour, stays. Still short once they have gone, the station empties archived chats' workspaces before their time ([station-storage.md](station-storage.md)). Only mirrors go this way: what tasks put elsewhere in the session's directory stays until the session's directory goes (archived, deleted, or 14 days unused). Chats had made a mirror of every worktree and kept them all, 204 of one session's on Studio and 112G of another's, and the stations' disks filled within hours (2026-10-20).
- A chat can ask the target to list its own mirrors with `station_task {station, action: "mirrors"}`, then remove one by its listed name with `station_task {station, action: "clean", mirror}`. The target checks under the session's lock that no task or sync uses it, marks prepared tasks to sync it again, and removes it itself. A large removal answers `{pending: true}` and continues; the same request takes up that removal rather than starting another. Everything in that mirror goes, including changed files and outputs not brought back; the agent must first preserve what it needs and choose only a mirror it is authorized to remove. Other chats' mirrors and non-mirror directories are out of reach. Older stations refuse the new actions.
- One task at a time per mirror: a sync or start while another task of the session runs there is refused (nothing starts). Tasks in other mirrors or without `dir` are not affected.
- After it ends, the source asks `task.files` for the `back` paths (a directory brings its files, at most 1000) and downloads them into `station-back/<key>/`, and asks `sync.changes` for synced files the command changed or removed. Those become `station-back/<key>/changes.patch` (`git diff --binary`, paths as `git apply` takes them in `dir`, old contents from `dir` or its Git objects, at most 64 MiB of changed files). Nothing in `dir` is changed: the agent reviews the patch and applies it if wanted. Both are in the completion notice (`back`).
- Compatibility: `describe` answers `sync: 1`. A source preparing with `dir` asks it first and refuses a station without it (an older one would run the command without the files); a start whose `sync.begin` is refused as unsupported starts nothing. A target starts a task with `dir` only after a sync committed for it. Tasks without `dir` and older sources are unchanged; `back` against an older target downloads the paths as files.
- Not done yet: taking contents from a Git repository already on the target (`git cat-file`) instead of sending them; resuming an interrupted sync's pieces (it starts over).

The source persists a receipt before sending start, follows task status across network and process restarts, and delivers completion/log tails and `stillfail-job notify` notices to the originating session. Nothing asks about a task while nothing happens to it: its start names the receipt (`push`, the receipt's file name), and the target tells the source each time the task ends or says something (`task.changed {workspace, ref}`, answered `{taken: true}` at once; `station/src/jobs/remote.ts` `pushOut`). The source then asks that task's station what (`task.gets`, below), so only the task's own station is believed. The target keeps in the task's record what it last told (`pushed`, a hash of the job's state and notices): a source not reached is told again after 1 s, doubling, at most a minute apart, until it is, and a target that starts again tells every source what it missed. A source that starts again asks once about all the tasks it has not told yet, those on one station in one request. A start whose answer did not come (uncertain) is asked about once, ten minutes on (a task its station started says something before). A start answered `push: true` tells of itself; a station from before it answers without, and is asked about the task every five seconds as before (the first time five seconds after the start), until its answer says `push`. Every such request names all the tasks followed on one station (`task.gets` with `tasks: [{session, key}]`, at most 200, answering each with what `task.get` would or its `error`, with `push: true` where the task tells of itself; a station from before it refuses it, and is then asked about each task with `task.get`). A task the station does not know (`unknown task`: its prepare or start never got there), or knows but has not started, ten minutes after the start was asked for is told to its session once and no longer followed (`lost` in the receipt): followed for good, ninety such tasks once kept a loaded station from answering anything else (2026-10-21). Notifications may be repeated if the source crashes between delivery and saving the receipt. Compatibility: nothing to deploy first and no data changed; both stations need this version for a task to tell of itself.

The target answers each source session's requests that change something (prepare, start, stop, uploads, syncs, downloads, closing it) one after another, and those of different sessions, and those that only read (`task.get`, `task.gets`, `task.log`, `task.list`), at once. Calls to one station share one connection, dialed once however many requests are waiting; a request not answered in 30 s leaves the connection open while the other station is heard (its answer is late), and closes it when it is not.

A task is keyed by **workspace + source station + source session + caller key**. A different peer or session cannot read, stop or fetch its files through this service. The remote job record is durable before process spawn. If a process disappears during a station/machine failure and no exit status can be recovered, it becomes `failed` with a null exit code; it is **not automatically re-executed**. That result is uncertain, not evidence that the command had no effects. Inspect it and use a new key only when another execution is intended.

Task files and records remain under the target's data directory `remote/incoming`; source receipts are under `remote/outgoing`. Remote long-lived services and delegating to another model are not provided in this first service.

## Chats on other stations

Any station of the workspace may read another's chats and write to its sessions; as with tasks, workspace membership is enough.

- `chat_read` / `session_history` with a chat's link on another station ask it (`session.read`). Its answer lists the attachments of the messages read; the reader fetches each (`session.file`) into its session's `uploads/<station>/` and names them by their path there, each whole after one answer (`whole: true`; from a station from before, in chunks). Those up to 16 MB come by themselves (up to 64 MB per read); larger ones are fetched when the agent names them in `fetch`. `session.file` gives only a file in the uploads directory of one of that chat's sessions — the files its page shows, also from an archived workspace — never another path.
- `session_send` to a session on another station sends its `files` first (`session.put`, at most 10 of 50 MB each, each whole after its request; to a station from before, in chunks), staged under the target's data directory `remote/staged`, then the message naming them (`session.message`); the target moves them into the uploads of the chat's agent and posts them with the message. Files no message claims are removed after a day. On the same station the files are copied there directly.

- `chat_create` with `station` opens a chat on another station (`session.create`): a new session in a still.fail chat of its own there, made once per the opener's session and key (`opened_chats` on both stations records who opened what). The answer says whether the opener's first message has come yet; if not, the opener sends it as `session_send` sends (`session.put`, then `session.message` with `opened: true`, which heads it as the chat's opening). Calling again with the same key gives the chat made then and sends the first message only if it has not arrived, so an uncertain answer is repeated by the agent with its key; nothing is resent by itself. Each time a turn of that chat ends all_done or need_human (or fails, or a person stops it), its station tells the opener's (`session.notice`), which accepts it only for a chat it recorded opening there and gives it to the opener as a station notice. If that station cannot be reached, the chat says so instead; the notice is not sent again. The opened chat's starter is the person who started the opener's chat. An agent keeps at most 8 chats it opened going at once (not ended all_done), and a chat opened this way opens none. Without a model named, the chat runs what its starter has opened most chats with on the station it is opened on, over 30 days, of the models the profiles there run for its workspace (of the runtime, when named): chosen there (`choose`, `runtimeGiven` in `session.create`), never the opener's, which that station may not run. It has to lead clearly, used at least twice as often as any other; when another is close (used more than half as often), or none was used and there are several, nothing is opened and the agent is told them, to ask the person (`station/src/sessions/model-choice.ts`). A station from before this gets no model and runs the runtime's default.

A station from before these methods takes them for tasks and refuses them; the reader then gets the text and is told the files were left there, and a message with files is not sent.

## Data outflow of the workspace

A program on one station's machine granted the whole workspace's data there ([data-outflow.md](data-outflow.md)) reads another station's through that station (`outflow.read`: `{op, args}`, `op` one of `outflowUsage`, `outflowChats`, `outflowMessages`). The station asked answers the chats of the workspace the request names, as its own program would read them (a span of usage of 31 days at most, a page of messages of 500 at most), the answer's JSON as the bytes after its head (`stillfail/station/2` only: a station from before has no such method and refuses it). As with chats, workspace membership is enough; the grant and its admin's answer are the asking station's.

## Shares

Stations also share profiles and skills over this transport (`share.get`, `share.lend`, `share.status`, `share.put`, `share.take`; [station-share.md](station-share.md)). Any station of the workspace may ask; what each share allows is checked by its host, which keeps it (still.fail cloud keeps nothing of shares).

## Chats shared with other workspaces

A chat may be shared with other workspaces ([chat-share.md](chat-share.md)). Its station then also hears the stations of those workspaces over this transport, though they are not in its roster: each request must name its workspace, and only `xshare.*`, reads of the chats shared with theirs (`session.read`, `session.file`) and, where allowed, writes to them (`session.put`, `session.message`) are answered; tasks, `session.create` and `session.notice` are not. A station of another workspace is asked only when a chat is shared with it or from it (`xshare/index.ts` decides; `peer.ts` checks), and may answer a session here that wrote to it. Which stations those workspaces have is kept between the stations, not by the control plane.

## Web services of other stations

A program on a station reaches an HTTP or WebSocket service listening on another station's localhost through its own station's agents' door, with no port opened on either machine:

`http://127.0.0.1:<door port>/peer/<station>/<port>/<path>?<query>` is `http://localhost:<port>/<path>?<query>` on that station. For example `OLLAMA_HOST=http://127.0.0.1:<door port>/peer/studio/11434`.

- The door is the agents' MCP endpoint's (`http://127.0.0.1:<port>/mcp`); the base is that URL with `/mcp` replaced by `/peer`. Claude sessions and jobs started from now on have it as `STILLFAIL_PEER_HTTP` (Codex sessions build it from their MCP URL).
- `<station>`: a station's id, or its name in any case (URL-encoded). The door is not a session's, so it knows no chat's workspace: it looks among the stations of every workspace this station is in, and refuses a name more than one station has (409; the id tells them apart) and this station itself (400). The request goes in the first of those workspaces that has the station (the home one first).
- Only programs on this machine: the door takes `/peer` requests only with `Host` 127.0.0.1, localhost or [::1] at its port (a site's page renamed to 127.0.0.1 by DNS rebinding still says its own Host), and without an `Origin` (or `Origin: null` with no `Sec-Fetch-Site` other than `none`: a sandboxed frame of a web page says both). People's browsers use a job with a port, as before.
- What goes: the method, the path and query as asked, every header but the hop's (`Connection` and those it names, `Transfer-Encoding`, `Upgrade`, `TE`, `Trailer`, `Keep-Alive`, `Host`); `Host` becomes `localhost:<port>` there, `Authorization` and `Accept-Encoding` go as given. The answer comes back with the service's status and headers (the hop's left out); a redirect to the service itself (`Location` `http://localhost:<port>/…` or `/…`) stays under its `/peer` path. Bodies stream both ways as they come, at the pace the slower side takes them (an event stream's head and each event as soon as the service sends them; uploads and downloads of any size, nothing held whole); a request whose answer is complete stops its upload. A `WebSocket` upgrade is opened on the service first, then taken at the door with the sub-protocol the service chose; messages and closes pass both ways.
- The other station refuses its own ports (its agents' door, its loopback port and, behind a launcher's entrance, those): 403.
- Errors are plain text: 404 no such station (naming the stations there are), 503 the roster is not current, 403 that station refused (not in its roster), 502 cannot be reached or no service answers on the port (the station there says so), 502 "needs an update" for a station from before this, 504 when it takes no connection within 20 s (offline).
- Transport: ALPN `stillfail/http/1`, admitted like the station transport (the caller's iroh key in the current roster, fail closed while it is not current; a station taken out of the workspace has its connections ended; losing still.fail cloud alone ends nothing). One request a QUIC stream: a JSON head line `{workspace, port, method, path, headers, body}` (headers as `[name, value]` pairs; `body` whether one follows) and the body until the stream finishes; answered with a JSON head line `{status, headers}` and the body. A WebSocket's head has `socket: true` and is answered 101, then its messages in a preview's socket frames (a kind byte, a 4-byte length, the payload). The station there reaches its service as a preview does (`station/src/jobs/preview.ts`). The caller offers `stillfail/station/1` after it: a station from before answers in that one (an endpoint picks by its own order, so a station lists `stillfail/http/1` before it), which is how "needs an update" is told. Code: `station/src/mesh/peer-http.ts`, the door's route in `station/src/tools/http.ts`.
- Compatibility: nothing to deploy first, no data changed. Both stations need this version; an older caller has no `/peer` route (404 from its door).
- Measured on one machine (studio, both stations in one Node process over real local iroh): a GET p50 0.9 ms (0.2 ms direct), a WebSocket echo p50 0.2 ms, a 100 MB download about 110 MB/s.

The path form suits programs that take a base URL. It does not suit web pages: a page's absolute paths (`/assets/…`), client routing, redirects to `/login` and cookie paths all lose the `/peer/<station>/<port>` prefix, and browsers are refused anyway (their `Origin`). For those, and for anything that is not HTTP, a port is forwarded instead.

### Forwarded ports

An agent forwards a port of another station to this machine with the `peer_forward` tool, as `ssh -L` does: `peer_forward {station, port, local_port?, job?}` opens a listener on `127.0.0.1:<local_port>` here, each connection to it carried as raw TCP to `localhost:<port>` on that station. Nothing about the traffic changes (paths, `Host`, cookies, WebSockets, any protocol), so web pages, dev servers with hot reload, `psql`/`redis-cli`, a Chrome's DevTools port work as on that machine. `peer_forward {}` lists the session's forwards (each with whether its station answers now); `peer_forward {close: <local_port>}` closes one.

- Where: 127.0.0.1 only (never another interface), at the same port number when nothing here listens on it at 127.0.0.1 or [::1] (where `localhost` may go first), else at `local_port` when given (an error when that one is taken), else any free port; the answer gives the address and URL (`http://127.0.0.1:<port>/`).
- Whose, and how long: a forward is the session's that opened it. It closes when that chat is archived or deleted, when the job given as `job` ends (stopped, failed, or a command that exited; a service that exited is started again, so its forward stays), after 30 minutes with no connection (the station's clock), or when the station stops. None survives a restart or a handover to the next station process: the agent opens it again. A session asking again for a port it forwards already gets the same forward.
- Who may: as `/peer`. The station there is named as in `/peer` (id or name among this station's workspaces), and admits the connection as it admits a `/peer` request (the caller in its roster). It refuses its own ports (agents' door, loopback port, launcher entrance ports) and the ports of its own forwards (a forward reaching another would carry on, or loop between two stations that forward to each other): the tool says so when opening. Opening asks that station once (a probe), so an old station, a refused port or a station not admitting this one is the tool's error, not every connection's.
- On that station: the connection goes to `localhost:<port>` as a local client's does, trying 127.0.0.1 and then [::1] (some servers listen on one alone: wrangler and others only on [::1]). Nothing listening there: that connection here is reset, the forward stays (a dev server may come up later); a listing gives the last error.
- Streams: bytes both ways as they come, each way at the pace the slower side takes them (a socket is read only as fast as the mesh stream takes its bytes, a stream only as fast as the socket takes them; nothing held whole); either side's end is passed on as a half-close, the other way still flowing; a reset or a socket error on either side resets both (the program here sees its connection reset).
- That station offline: the listener stays. A connection that cannot reach the station is reset, and for 10 s after, further connections are reset at once rather than each waiting for the mesh to give up; a listing says `offline: …`.
- Wire: on `stillfail/http/1` (above), one connection a QUIC stream: a JSON head line `{workspace, port, tcp: true}` answered `{status: 200}` once the station there has connected to the port, then the bytes; a refusal is answered as a `/peer` one (`{status, headers}` and words). A probe's head adds `probe: true` and is answered 200 or refused, nothing connected. A station from before this answers in `stillfail/station/1` and is reported as needing an update. Code: `station/src/mesh/peer-forward.ts` (listeners, lifetimes, the byte pump), `station/src/mesh/peer-http.ts` (both sides of the stream), the tool in `station/src/tools/forward.ts`.
- Compatibility: as `/peer`, both stations need this version (an older target is "needs an update", an older caller has no `peer_forward`); nothing to deploy first, no data changed.
- Tests: `station/test/peer-forward.test.ts` (memory mesh with flow control, a test clock); end to end on a dev cloud with two real stations, `station/side/peer-forward-e2e.ts` (Chromium opens a forwarded page with absolute asset paths and a WebSocket when `PLAYWRIGHT_MODULE` is given). Measured there (studio, two station processes over real local iroh): a GET p50 0.36 ms on a kept connection (0.16 ms direct), 0.73 ms on a new connection each time; a WebSocket echo p50 0.31 ms; raw TCP about 90 MB/s down and 80 MB/s up.

## Transport

ALPN `stillfail/station/2` is separate from the member/admin protocol (web services go on their own, `stillfail/http/1`, above). One request a QUIC bidirectional stream: a JSON head line `{workspace, request:{method,...}, bytes?}`, and with `bytes: true` the request's bytes until the stream finishes; answered by a JSON head line `{result, bytes?}` or `{error}`, and with `bytes: true` the answer's bytes. Bytes are a file as it is read, sent at the pace the other end takes it: nothing in base64, no chunks, no round trip but the request's. A reader that stops early resets the stream, and its sender stops; a sender whose bytes fail on the way (the file changed) resets it, and the reader fails. Before 2026-10-29 the transport was `stillfail/station/1`: a whole JSON `{workspace, request}` (1 MiB at most) the caller finishes, a whole JSON `{result}` or `{error}` back, and files went as base64 in 256 KiB chunks, one round trip each, so at most 256 KiB a round trip (about 1.3 MB/s at 200 ms). A station offers `/2` first and lists it before `/1`; a station from before answers in `/1`, and is asked and sent files as then (`NoBytes` when a request with bytes would go to it: the caller sends chunks). Code: `station/src/mesh/peer.ts`, `station/src/mesh/files.ts`. Services accept explicit methods (`describe`, `task.*`, `file.*`, `sync.*`); this is not an arbitrary management-path proxy. Network timeouts explicitly report uncertain execution. The transport can carry further services without encoding build-specific concepts.

Tests exercise workspace roster isolation/removal, real local iroh connections with temporary station data, task ownership, repeated starts, file transfer, cancellation and removal from the workspace. No production station is used for verification.
